# CORS 면접 스터디 문서 설계

## 목적

백엔드 개발자 면접을 준비하는 스터디원이 CORS를 단순한 설정 문제가 아니라 브라우저 보안 정책과 HTTP 통신 흐름의 관점에서 설명할 수 있게 한다. 발표 시간은 저장소 운영 방침에 맞춰 10~20분을 기준으로 한다.

- 설명 언어: 한국어
- 예시 방향: 프레임워크에 독립적인 HTTP 메시지와 Java/Spring 설정을 함께 사용

## 독자와 학습 목표

독자는 웹과 HTTP의 기초를 학습한 백엔드 개발자 지망생으로 가정한다. 문서를 읽은 뒤 다음 내용을 설명할 수 있어야 한다.

- Origin의 구성과 Same-Origin Policy가 필요한 이유
- CORS가 보안 정책 자체가 아니라 교차 출처 읽기를 허용하는 HTTP 기반 메커니즘이라는 점
- 브라우저, 프런트엔드 코드, 서버가 각각 담당하는 역할
- 단순 요청과 Preflight 요청의 조건 및 처리 흐름
- 주요 요청·응답 헤더의 의미
- 쿠키나 인증 정보를 포함하는 요청의 제약
- Spring MVC와 Spring Security에서 CORS를 설정하는 방법
- 흔한 오류를 브라우저 개발자 도구와 HTTP 메시지로 진단하는 방법
- 면접의 기본 질문과 꼬리 질문에 짧고 정확하게 답하는 방법

## 핵심 설명 원칙

- CORS 적용 여부는 서버가 응답 헤더로 허용 범위를 표현하고 브라우저가 이를 검사한다는 구조로 설명한다.
- `curl`, Postman, 서버 간 통신에서는 브라우저의 Same-Origin Policy가 적용되지 않는다는 차이를 명시한다.
- Preflight가 인증·인가나 공격 차단을 대신하지 않으며, 일부 요청은 실제 요청이 먼저 전송된 뒤 응답 읽기만 차단될 수 있음을 설명한다.
- 단순 요청의 정확한 조건을 메서드, 헤더, `Content-Type` 기준으로 정리한다.
- `Access-Control-Allow-Origin: *`와 자격 증명 요청을 함께 사용할 수 없다는 제약을 다룬다.
- 요청 Origin을 검증 없이 그대로 응답하는 위험한 설정을 피하도록 안내한다.
- CORS와 CSRF를 구분하고, CORS만으로 서버의 보안을 보장할 수 없음을 설명한다.

## 예시와 표현 방식

- `https://frontend.example`에서 `https://api.example`로 요청하는 일관된 사례를 사용한다.
- HTTP 요청과 응답은 코드 블록으로 제시한다.
- 단순 요청과 Preflight 요청은 비교 표와 순서가 드러나는 텍스트 흐름으로 설명한다.
- Spring 예시는 전역 설정과 특정 컨트롤러 설정을 구분한다.
- Spring Security를 사용하는 경우 CORS 처리가 보안 필터 체인과 연결되어야 함을 별도로 보여준다.
- 설정 코드는 최소한으로 유지하되 허용 출처, 메서드, 헤더, 자격 증명 옵션의 의미를 함께 적는다.

## 정확성 및 검증 기준

- Fetch 표준, MDN, Spring 공식 문서처럼 공식 또는 일차 자료를 우선한다.
- Simple Request는 표준의 용어인 CORS-safelisted request에 대응함을 밝힌다.
- 헤더 이름과 예제 HTTP 메시지를 대소문자·문법 관점에서 점검한다.
- Spring 예제는 현재 공식 문서의 구성 방식과 대조한다.
- 완성 후 Markdown 구조, 내부 링크, 코드 블록, 남은 임시 문구를 검사한다.

## 제외 범위

- 브라우저별 과거 구현 차이의 상세 연혁

- Nginx, API Gateway, CDN 제품별 설정법
